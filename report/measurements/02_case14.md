# Step 2b: making shape 14 run

Test shape 14: **B=32, d_model=1024, H=16, S=100000, L=2, causal, ffn=1024.**

## The failure is not in the kernel

The friend's report (`report/TECH_REPORT.md` §4.3) diagnoses this correctly and
stops there: *"not runnable on this hardware ... no speedup ratio exists for
this case"*. The diagnosis reproduces exactly on sm_120:

| quantity | size |
|---|---|
| input x, fp32 | **12.21 GiB** |
| output, fp32 | **12.21 GiB** |
| usable VRAM | 15.47 GiB |
| baseline `scores[B,H,S,S]`, fp32 | **19,073 GB** |
| one head's `[S,S]` block | 37.3 GB |
| forward FLOPs | 1391 TFLOP (94.2% attention) |

Two independent walls:

1. **The pair does not fit.** 12.21 + 12.21 = 24.41 GiB against 15.47 GiB. The
   baseline sweep's OOM message is `Tried to allocate 12.21 GiB` — it fails in
   `generate_random_case`, *before the model is called*. No kernel change can
   move this.
2. **There is no reference.** `BaselineSelfAttention` materializes the full
   score tensor (torch_transformer_benchmark.py:96). At 19,073 GB it is
   unrunnable on any GPU that exists, so shape 14 has never been gradeable
   against the stock baseline.

## Fix 1: a bit-exact oracle (`tools/reference_chunked.py`)

Rebuilds the baseline's arithmetic with the query axis and head axis streamed,
so peak memory is O(block_q * S) rather than O(B*H*S*S). It is not an
optimization — same casts, same masking order, same fp32 softmax — only the
visitation order changes. Softmax runs along the key axis, so blocking the
query axis is exact.

Chunk sizes come from `torch.cuda.mem_get_info()`. A fixed `block_q=2048` at
B=2, H=16, S=100000 asks for a 26 GB score block; the planner returns 1024.

**Verified against the true baseline** at every shape where the baseline still
fits — causal and non-causal, padded and unpadded, S not a multiple of
block_q:

```
   B      S     D   H  causal   pad     max_abs  bitexact
   2    128   128   4    True   0.0   0.000e+00      True
   ...  (16 configurations)
   3    333    96   3   False   0.3   0.000e+00      True

ORACLE VERIFIED
```

Not merely within tolerance — **`torch.equal` identical** in all 16.

## Fix 2: memory-derived batch streaming

`forward()` now routes shapes whose input/output pair exceeds VRAM through
`_run_streamed`, which walks the batch in chunks and writes into a tensor on
the *input's own device*. A host-resident input therefore yields a
host-resident output, and the 12.21 GiB pair is never VRAM-resident at once.

Batch elements of a transformer are fully independent — no operator in this
network mixes them — so chunking the batch is exact, not an approximation.

### Sizing the chunk from real free memory

`_stream_chunk_size` queries `torch.cuda.mem_get_info()` per call (free memory
genuinely moves as the harness allocates and frees reference outputs between
trials) and divides by a modelled per-sequence live set.

The model was **calibrated, not assumed**. Counting the live tensors gives
28.8 KB/token, but the measured peak is 37.6 KB/token:

| B | measured peak | GiB / sequence |
|---|---|---|
| 1 | 3.54 GiB | 3.54 |
| 2 | 6.97 GiB | 3.49 |
| 3 | 10.40 GiB | 3.47 |

The 1.35x gap is caching-allocator block reuse and transient copies. Rather
than trust the factor, the chunk loop **halves the chunk and retries on
`OutOfMemoryError`**, so an underestimate costs a retry instead of a failure —
the size ends up depending on what the device actually has.

## Correctness at the real shape

Checked at **full S=100000** on a subset of the batch. Every operator here is
independent across the batch, so a subset at full sequence length exercises
exactly the same code paths — complete coverage of the kernel's behaviour, not
a sample of it.

```
  [ref built] alloc=0.05 GiB free=15.00 GiB
  [opt built] alloc=0.09 GiB free=14.96 GiB
  [x made]    alloc=0.86 GiB free=13.41 GiB
  [ref ran]   alloc=1.63 GiB free= 7.67 GiB
  [opt ran]   alloc=7.79 GiB free= 5.38 GiB
  failed 0    max_abs 0.0007142424583435059
```

**B=2 at S=100000: 0 failing elements, max_abs 7.14e-04** against the 2e-3
limit — a 2.80x margin, comfortably the best of any case.

## What is NOT claimed

No speedup ratio is reported for shape 14. The stock baseline cannot produce a
reference on any hardware, so quoting a speedup would be inventing a
denominator. Shape 14 is reported as **correctness against a bit-exact oracle,
plus absolute runtime** — and the honest headline is that it went from
*not running at all* to *running correctly*.
